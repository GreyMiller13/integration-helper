# OWASP API Security Top 10 (2023)

OWASP API Security Top 10 — рейтинг самых распространённых и опасных рисков безопасности API от сообщества OWASP. Актуальная редакция — 2023 года. Для аналитика это готовый список того, что нужно явно закрыть требованиями: большинство пунктов — не ошибки кода, а **пробелы в постановке** (не описали, кому какой объект доступен, какие поля можно менять, какие лимиты действуют).

## Список рисков {#list}

| Код | Название | Кратко |
|---|---|---|
| API1:2023 | [Broken Object Level Authorization](#api1) | Доступ к чужим объектам по их ID |
| API2:2023 | [Broken Authentication](#api2) | Слабая или сломанная аутентификация |
| API3:2023 | [Broken Object Property Level Authorization](#api3) | Чтение или изменение запрещённых полей объекта |
| API4:2023 | [Unrestricted Resource Consumption](#api4) | Нет лимитов на ресурсы и стоимость операций |
| API5:2023 | [Broken Function Level Authorization](#api5) | Доступ к запрещённым функциям (админским методам) |
| API6:2023 | [Unrestricted Access to Sensitive Business Flows](#api6) | Автоматизированное злоупотребление бизнес-процессом |
| API7:2023 | [Server Side Request Forgery](#api7) | Сервер ходит по URL, заданному атакующим |

## API1:2023 Broken Object Level Authorization {#api1}

**Суть.** API принимает идентификатор объекта от клиента и не проверяет, имеет ли вызывающий право на **этот** объект. Самая распространённая и опасная уязвимость API (BOLA, ранее IDOR).

**Пример сценария.** Клиент 1001 авторизован и запрашивает свою выписку, затем меняет ID:

```http
GET /api/v1/accounts/1002/statements HTTP/1.1
Authorization: Bearer токен_владельца_счёта_1001
```

Сервер проверил токен (аутентификация пройдена), нашёл счёт 1002 и вернул его — чужие данные раскрыты. То же для `PUT`, `DELETE`, для ID в теле запроса, в query-параметрах, в вложенных ресурсах (`/orders/42/items/7`).

**Как предотвратить:**

- проверка прав на объект в **каждом** методе, принимающем ID, через единый механизм авторизации;
- принадлежность определять по данным с сервера (владелец объекта в БД) и по субъекту из токена, а не по параметрам запроса (`?userId=`);
- непредсказуемые ID (UUID) как дополнительная мера, но не замена проверки;
- автотесты с двумя пользователями: пользователь A не может прочитать и изменить объекты пользователя B.

**Что прописать в требованиях:** для каждого ресурса — правило доступа («заказ доступен клиенту, если `order.customerId = sub` из токена; оператору — если заказ в его регионе»), код ответа при отказе (403 или 404), обязательный негативный тест.

## API2:2023 Broken Authentication {#api2}

**Суть.** Механизмы аутентификации реализованы неправильно: можно подобрать пароль, подделать токен, использовать украденные учётные данные.

**Примеры:**

- endpoint входа или восстановления пароля без ограничения попыток — перебор паролей (credential stuffing);
- JWT принимается без проверки подписи, с `alg: none`, без проверки `exp` или `aud`;
- API key передаётся в URL и оседает в логах;
- смена e-mail или пароля без повторного подтверждения текущим паролем;
- долгоживущие токены без возможности отзыва.

**Как предотвратить:**

- стандартные протоколы ([OAuth 2.0](/security/oauth2), OIDC) и проверенные библиотеки вместо самописных схем;
- ограничение попыток, блокировки, CAPTCHA и MFA для пользовательских сценариев;
- полная [проверка JWT](/security/jwt): подпись, алгоритм из allowlist, `iss`, `aud`, `exp`;
- короткоживущие токены, ротация и отзыв секретов;
- все endpoint аутентификации (вход, восстановление, обновление токена) рассматривать как отдельную поверхность атаки.

**Что прописать в требованиях:** способ аутентификации каждого клиента, сроки жизни токенов, лимиты на попытки входа и выдачу токенов, процедуру отзыва, требования к хранению паролей и секретов.

## API3:2023 Broken Object Property Level Authorization {#api3}

**Суть.** Доступ к объекту разрешён, но не контролируется доступ к **отдельным полям**. Объединяет два риска редакции 2019: избыточное раскрытие данных (Excessive Data Exposure) и массовое присвоение (Mass Assignment).

**Пример 1 — избыточное раскрытие.** API возвращает объект пользователя целиком, а фронтенд показывает только имя:

```json
{
  "id": 1001,
  "name": "Иван Петров",
  "passportNumber": "4510 123456",
  "passwordHash": "$2b$12$...",
  "isAdmin": false,
  "internalScore": 0.87
}
```

**Пример 2 — mass assignment.** Клиент добавляет в запрос поле, которое не должен менять, а сервер связывает тело запроса с моделью целиком:

```http
PATCH /api/v1/users/1001 HTTP/1.1
Content-Type: application/json

{"name": "Иван Петров", "isAdmin": true, "balance": 1000000}
```

**Как предотвратить:**

- ответ формировать по явному списку полей (DTO), а не сериализацией всей сущности; фильтрация на клиенте — не защита;
- для входящих данных — белый список изменяемых полей для каждой операции и роли;
- лишние поля в запросе — отклонять (`400`) или игнорировать — решение фиксируется в спецификации;
- `additionalProperties: false` в схеме OpenAPI там, где это уместно;
- поля только для чтения (`readOnly`) — `id`, `status`, `createdAt`, `balance` — не принимаются в запросах.

**Что прописать в требованиях:** для каждой операции — какие поля возвращаются и какие можно передать (по ролям), какие поля только для чтения, поведение при лишних полях, какие поля содержат ПДн и где их нужно маскировать.

## API4:2023 Unrestricted Resource Consumption {#api4}

**Суть.** Отсутствие ограничений на ресурсы: процессор, память, сеть, хранилище, а также **платные** операции (SMS, e-mail, вызовы платных сторонних API). Результат — отказ в обслуживании или прямые финансовые потери.

**Примеры:**

- `GET /orders?limit=1000000` — выгрузка всей базы одним запросом;
- загрузка файла на 10 ГБ или JSON с глубиной вложенности 10 000;
- endpoint «отправить SMS с кодом» без лимитов — атакующий разоряет компанию на SMS;
- пакетный запрос на 100 000 операций, GraphQL-запрос с глубокой вложенностью.

**Как предотвратить:**

- [rate limiting](/design/rate-limiting) по клиенту, пользователю, IP, а для дорогих операций — отдельные лимиты и квоты;
- максимальный размер тела, файла, массива, строки, глубины вложенности;
- максимальный размер страницы в [пагинации](/design/pagination), лимит элементов в [пакетных операциях](/design/bulk);
- таймауты выполнения, ограничения на ресурсы контейнеров;
- лимиты на расходы у провайдеров (SMS, облако) и алерты.

**Что прописать в требованиях:** лимиты запросов на клиента и коды ответа ([429](/http/status-codes#429) с `Retry-After`, [413](/http/status-codes#413)), максимальный `limit` страницы, размеры полей и файлов, лимиты на платные действия.

## API5:2023 Broken Function Level Authorization {#api5}

**Суть.** Не проверяется право вызывающего на **функцию** (операцию): обычный пользователь может вызвать административный метод, партнёр — внутренний.

**Пример сценария.** Пользователь видит в мобильном приложении `GET /api/v1/users/me` и пробует соседние варианты:

```http
GET /api/v1/admin/users HTTP/1.1
DELETE /api/v1/users/1002 HTTP/1.1
POST /api/v1/users/1001/roles HTTP/1.1
```

Если сервер проверяет только наличие валидного токена, а не роль — атакующий получает административные функции. Часто админские методы «спрятаны» в отдельном пути, но доступны из того же шлюза.

**Как предотвратить:**

- по умолчанию доступ запрещён (deny by default), права выдаются явно для каждой операции;
- авторизация на уровне операций — централизованно (политики на шлюзе или в общем модуле), а не вручную в каждом обработчике;
- административные и внутренние API — на отдельном хосте или в отдельном сетевом контуре, недоступном снаружи;
- автотесты: каждая роль против каждой операции.

**Что прописать в требованиях:** матрица «роль/клиент/scope → операция (метод + путь)», разделение публичных, партнёрских и внутренних API.

## API6:2023 Unrestricted Access to Sensitive Business Flows {#api6}

**Суть.** Технически всё корректно, но бизнес-процесс можно **автоматизировать во вред** бизнесу: скупка товара ботами, массовая регистрация, накрутка бонусов, бронирование всех мест без оплаты.

**Примеры:**

- бот выкупает всю партию дефицитного товара в первые секунды продаж для перепродажи;
- массовое создание аккаунтов ради приветственного бонуса;
- бронирование всех слотов на месяц вперёд без оплаты, чтобы заблокировать конкурентов;
- спам отзывами или заявками.

**Как предотвратить:**

- определить чувствительные бизнес-процессы и оценить, чем грозит их автоматизация;
- антибот-механизмы: отпечаток устройства, CAPTCHA, поведенческий анализ, проверка человека для чувствительных шагов;
- бизнес-лимиты: «не более N единиц в одни руки», «не более N бронирований без оплаты», время удержания брони;
- для машинных интеграций — отдельные API с договорными квотами вместо использования пользовательского API.

**Что прописать в требованиях:** перечень чувствительных бизнес-процессов, бизнес-ограничения (на пользователя, карту, устройство, адрес доставки), мониторинг аномалий.

## API7:2023 Server Side Request Forgery {#api7}

**Суть.** API принимает от клиента URL (картинка по ссылке, адрес вебхука, импорт файла) и сервер сам по нему обращается. Атакующий указывает внутренний адрес и заставляет сервер обратиться к ресурсам, недоступным снаружи.

**Пример сценария:**

```http
POST /api/v1/webhooks HTTP/1.1
Content-Type: application/json

{"url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}
```

При проверке вебхука сервер обращается к сервису метаданных облака и может вернуть или раскрыть временные учётные данные. Варианты: `http://localhost:8080/admin`, `http://10.0.0.5:6379`, `file:///etc/passwd`, перенаправления (`302`) с внешнего адреса на внутренний, DNS rebinding.

**Как предотвратить:**

- по возможности не принимать произвольные URL: выбор из заранее зарегистрированных адресов, загрузка файла вместо ссылки;
- белый список схем (только `https`), доменов и портов;
- запрет обращений к приватным, loopback и link-local адресам **после** разрешения DNS (и повторная проверка при каждом перенаправлении или отключение перенаправлений);
- исходящие запросы — через выделенный egress-прокси с собственными правилами;
- не возвращать клиенту сырой ответ стороннего сервера;
- в облаке — защищённые версии сервиса метаданных (например, IMDSv2 в AWS).

**Что прописать в требованиях:** где API принимает URL, какие схемы и домены допустимы, таймауты и максимальный размер загрузки, политика перенаправлений, сетевая изоляция исходящих запросов.

## API8:2023 Security Misconfiguration {#api8}

**Суть.** Небезопасные настройки на любом уровне: сервер, шлюз, фреймворк, облако, контейнер.

**Примеры:**

- стектрейсы, версии ПО и SQL-запросы в ответах с ошибками;
- включённые отладочные endpoint, Swagger UI и actuator в проде без защиты;
- слабая конфигурация TLS, HTTP без перенаправления;
- CORS с отражением любого `Origin` и `Allow-Credentials: true`;
- отсутствие заголовков безопасности, учётные записи и пароли по умолчанию;
- неустановленные обновления безопасности, открытые бакеты хранилищ.

**Как предотвратить:**

- воспроизводимая конфигурация (infrastructure as code) с ревью и одинаковыми настройками окружений;
- hardening: отключение лишних методов, функций, endpoint, учётных записей по умолчанию;
- единый формат [ошибок](/design/errors) без внутренних деталей;
- [TLS](/security/tls) с актуальными версиями, корректный [CORS](/security/cors), заголовки безопасности;
- регулярное сканирование конфигурации и управление обновлениями.

**Что прописать в требованиях:** формат ошибок и запрет внутренних деталей в них, доступность документации и служебных endpoint по окружениям, требования к TLS, CORS и заголовкам.

## API9:2023 Improper Inventory Management {#api9}

**Суть.** Организация не знает, какие API, версии и окружения у неё есть. Забытые старые версии (`/v1` без исправлений, сделанных в `/v2`), тестовые стенды с боевыми данными, недокументированные endpoint и неучтённые потоки данных к третьим сторонам.

**Примеры:**

- в `/api/v2` исправили BOLA, а `/api/v1` всё ещё работает и уязвим;
- `beta-api.example.com` смотрит на продуктивную базу и не закрыт аутентификацией;
- партнёр получает больше данных, чем описано в договоре, потому что никто не вёл учёт.

**Как предотвратить:**

- реестр (каталог) API: владелец, назначение, версии, окружения, потребители, классификация данных;
- актуальная спецификация [OpenAPI](/specs/openapi) для каждого API, генерируемая или проверяемая в CI;
- политика [версионирования](/design/versioning) и вывода из эксплуатации (deprecation, sunset) старых версий;
- тестовые окружения — без боевых данных и с теми же мерами защиты;
- учёт интеграций с третьими сторонами и передаваемых им данных.

**Что прописать в требованиях:** владельца API, версии и сроки их поддержки, перечень окружений, реестр потребителей и передаваемых им данных.

## API10:2023 Unsafe Consumption of APIs {#api10}

**Суть.** Разработчики доверяют данным от сторонних и партнёрских API больше, чем пользовательскому вводу, и не проверяют их. Атакующий компрометирует сторонний сервис (или выдаёт себя за него) и через него атакует вас.

**Примеры:**

- данные от партнёра вставляются в SQL-запрос без параметризации — SQL-инъекция «через партнёра»;
- интеграция слепо следует перенаправлениям стороннего API, в т. ч. на HTTP или во внутреннюю сеть;
- ответ стороннего API на 2 ГБ без ограничения размера приводит к исчерпанию памяти;
- сторонний API недоступен, а ваш сервис зависает без таймаутов.

**Как предотвратить:**

- валидировать ответы сторонних API по схеме, как пользовательский ввод: типы, размеры, допустимые значения;
- взаимодействовать только по TLS с проверкой сертификата;
- не следовать перенаправлениям вслепую;
- ограничивать размер ответа, задавать [таймауты и повторы](/reliability/timeouts-retries), применять [паттерны устойчивости](/reliability/resilience-patterns) (circuit breaker);
- оценивать безопасность поставщиков API и поддерживать список интеграций.

**Что прописать в требованиях:** схема и правила валидации входящих данных от партнёра, поведение при некорректных данных, таймауты, лимит размера ответа, поведение при недоступности партнёра.

## Сравнение с редакцией 2019 года {#vs-2019}

| 2019 | 2023 | Что изменилось |
|---|---|---|
| API1 Broken Object Level Authorization | API1 Broken Object Level Authorization | Без изменений — по-прежнему главный риск |
| API2 Broken User Authentication | API2 Broken Authentication | Расширено: аутентификация не только пользователей, но и машин |
| API3 Excessive Data Exposure | API3 Broken Object Property Level Authorization | Объединены в один риск на уровне свойств объекта |
| API6 Mass Assignment | API3 Broken Object Property Level Authorization | (см. выше) |
| API4 Lack of Resources and Rate Limiting | API4 Unrestricted Resource Consumption | Расширено: включает стоимость операций (SMS, платные API) |
| API5 Broken Function Level Authorization | API5 Broken Function Level Authorization | Без изменений |
| — | API6 Unrestricted Access to Sensitive Business Flows | **Новый** риск |
| — | API7 Server Side Request Forgery | **Новый** риск |
| API7 Security Misconfiguration | API8 Security Misconfiguration | Сдвиг позиции |
| API9 Improper Assets Management | API9 Improper Inventory Management | Переименован, акцент на учёте |
| API8 Injection | — | Исключён как отдельный пункт: учитывается в других рисках (в т. ч. API10) |
| API10 Insufficient Logging and Monitoring | — | Исключён из списка |
| — | API10 Unsafe Consumption of APIs | **Новый** риск |

Исключение Injection и Logging из списка не означает, что они больше не важны: защита от инъекций и аудит по-прежнему обязательны (см. [чек-лист безопасности](/security/best-practices)).

## На что обратить внимание аналитику {#analyst-checklist}

- [ ] Для каждого ресурса описано правило доступа к объекту (API1) и есть негативный тест «чужой объект».
- [ ] Описан способ аутентификации, сроки токенов, лимиты попыток входа (API2).
- [ ] Для каждой операции — списки возвращаемых и изменяемых полей, поля только для чтения, поведение при лишних полях (API3).
- [ ] Заданы лимиты: частота, размер тела, размер страницы, пакеты, платные операции (API4).
- [ ] Есть матрица ролей и операций, админские API изолированы (API5).
- [ ] Определены чувствительные бизнес-процессы и бизнес-ограничения против автоматизации (API6).
- [ ] Все места, где сервер ходит по URL от клиента, описаны с белыми списками (API7).
- [ ] Определены формат ошибок без внутренних деталей и требования к конфигурации (API8).
- [ ] API зарегистрирован в каталоге, описаны версии, окружения, потребители (API9).
- [ ] Данные от партнёров валидируются, заданы таймауты и лимиты размера ответа (API10).
