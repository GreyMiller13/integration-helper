# Соглашения о данных

Большинство интеграционных инцидентов — не про протоколы, а про данные: дата пришла без часового пояса, сумма округлилась во `float`, ИНН потерял ведущий ноль, большой идентификатор исказился в JavaScript. Эта страница — набор соглашений о представлении типовых данных в JSON API, которые стоит зафиксировать в спецификации **до** начала разработки.

## Сводная таблица {#summary}

| Тип данных | Рекомендуемый формат | Пример |
|---|---|---|
| Момент времени | RFC 3339, UTC (`Z`) или со смещением | `"2026-10-03T14:30:00Z"`, `"2026-10-03T17:30:00+03:00"` |
| Дата без времени | RFC 3339 `full-date` | `"2026-10-03"` |
| Время суток | `HH:MM:SS` (+ часовой пояс отдельно) | `"09:00:00"` |
| Часовой пояс | Идентификатор IANA | `"Europe/Moscow"` |
| Длительность | ISO 8601 duration | `"PT15M"`, `"P1DT2H"` |
| Денежная сумма | Строка-десятичное или целое в минорных единицах + валюта | `{"amount": "1234.50", "currency": "RUB"}` |
| Валюта | ISO 4217 alpha-3 | `"RUB"`, `"USD"` |
| Целое больше 2^53 | Строка | `"9223372036854775807"` |
| Идентификатор | Строка (UUID, ULID или иной) | `"01928f3c-5d2e-7a1b-9c4d-3e5f6a7b8c9d"` |
| Перечисление | Строка `UPPER_SNAKE_CASE` | `"PARTIALLY_PAID"` |
| Булево | `true` / `false` | `"isActive": true` |
| Пустой список | `[]`, не `null` | `"items": []` |
| Язык | BCP 47 | `"ru"`, `"ru-RU"`, `"en-GB"` |
| Страна | ISO 3166-1 alpha-2 | `"RU"`, `"KZ"` |
| Телефон | E.164 | `"+79161234567"` |
| Email | Строка, RFC 5322 (на практике — упрощённая проверка) | `"ivan.petrov@example.com"` |
| ИНН, КПП, ОГРН, БИК, счёт, СНИЛС | **Строка** (не число!) | `"0274062111"` |
| Двоичные данные | Base64 в строке (небольшие) или отдельный ресурс | `"JVBERi0xLjQK..."` |
| URI | Абсолютный URI | `"https://api.example.com/orders/42"` |

## Именование полей {#naming}

| Стиль | Пример | Кто рекомендует |
|---|---|---|
| `camelCase` | `createdAt`, `customerId` | Google AIP (JSON-представление), Microsoft REST API Guidelines, большинство JS/Java-экосистем |
| `snake_case` | `created_at`, `customer_id` | Zalando, Stripe, GitHub, Python-экосистема |
| `kebab-case` | `created-at` | Не используется для полей JSON (неудобно в коде); встречается в URI |

Главное — **один стиль во всём API**. Дополнительные правила:

- английские слова, без транслита (`inn` — допустимое исключение для устоявшихся российских реквизитов);
- аббревиатуры как слова: `customerId`, `httpUrl`, а не `customerID`, `HTTPURL`;
- имена коллекций — во множественном числе (`items`), булевы — с префиксом `is`/`has`/`can` (`isActive`, `hasChildren`);
- единицы измерения в имени, если они не очевидны: `weightKg`, `timeoutMs`, `distanceMeters`;
- суффиксы времени единообразны: `createdAt`/`updatedAt` для моментов, `birthDate`/`dueDate` для дат.

## Даты и время {#datetime}

### Момент времени {#timestamp}

Используйте **RFC 3339** — профиль ISO 8601 для интернет-протоколов. Он однозначнее ISO 8601: всегда полная дата, всегда смещение.

```json
{
  "createdAt": "2026-10-03T14:30:00Z",
  "paidAt": "2026-10-03T17:30:00.123+03:00"
}
```

- Всегда со смещением: `Z` (UTC) или `+03:00`. Время **без смещения** (`"2026-10-03T14:30:00"`) — главная ошибка: получатель интерпретирует его в своём часовом поясе.
- Рекомендуемая практика: сервер хранит и **отдаёт в UTC**, клиент конвертирует для отображения. Отдавать с местным смещением тоже корректно — главное, чтобы смещение было.
- Принимать стоит любое корректное смещение, а не только `Z`.
- Дробные секунды: договоритесь о точности (миллисекунды/микросекунды) и о том, что получатель обязан принимать любую.
- Разделитель `T` — заглавная буква; `Z` — тоже (RFC 3339 допускает строчные, но не все парсеры).

::: warning Смещение ≠ часовой пояс
`+03:00` — это смещение в конкретный момент, а не часовой пояс. Если нужно знать **правила** зоны (для расписаний, повторяющихся событий, отображения «по местному времени магазина»), передавайте отдельно IANA-идентификатор: `"timeZone": "Asia/Yekaterinburg"`. RFC 9557 (2024) расширяет формат RFC 3339 суффиксом с зоной: `2026-10-03T14:30:00+05:00[Asia/Yekaterinburg]` — но поддержка в библиотеках пока ограничена.
:::

### Дата без времени {#date}

Дата рождения, дата документа, дата действия тарифа — это **не момент времени**. Передавайте как `"2026-10-03"`.

::: danger Дата как полночь UTC
`"birthDate": "1990-05-15T00:00:00Z"` в часовом поясе UTC−5 превратится в 14 мая. Никогда не передавайте календарные даты как момент времени.
:::

### Время суток, часовые пояса, расписания

- Время суток: `"opensAt": "09:00:00"` + `"timeZone": "Europe/Moscow"`.
- Часовой пояс — идентификатор базы IANA (`Europe/Moscow`), а не аббревиатура (`MSK`, `EST` неоднозначны) и не фиксированное смещение (правила перехода меняются).
- Будущие события по местному времени (встреча в 10:00 через полгода) храните как местное время + зона, а не как UTC: если законодательство изменит смещение, UTC-время станет неверным.

### Unix timestamp {#unix-time}

| | RFC 3339 строка | Unix timestamp |
|---|---|---|
| Пример | `"2026-10-03T14:30:00Z"` | `1791037800` |
| Читаемость | Да | Нет |
| Однозначность | Да (со смещением) | Да (всегда UTC) |
| Единицы | Явные | Секунды или миллисекунды? — частая ошибка в 1000 раз |
| Даты до 1970 и после 2038 | Без проблем | Проблема 2038 года для 32-битных знаковых целых |
| Сравнение и арифметика | Нужен парсинг | Просто числа |
| Где уместен | **Бизнес-данные в API** | Технические поля: `exp`/`iat` в [JWT](/security/jwt), метрики, заголовки |

Если всё же используете Unix time — указывайте единицы в имени поля: `createdAtMs`, `expiresAtSec`.

### Длительности {#duration}

ISO 8601 duration: `P[n]Y[n]M[n]DT[n]H[n]M[n]S`.

| Значение | Смысл |
|---|---|
| `PT15M` | 15 минут |
| `PT1H30M` | 1 час 30 минут |
| `P1D` | 1 календарный день (не всегда 24 часа — переход на летнее время) |
| `P1M` | 1 календарный месяц (28–31 день) |
| `PT0.5S` | 500 миллисекунд |

Альтернатива для технических величин — число с единицей в имени: `"timeoutSeconds": 30`. Не передавайте длительность голым числом без единиц.

### Периоды

Для интервалов указывайте, включительна ли граница. Распространённое соглашение — полуоткрытый интервал: `from` включительно, `to` не включительно (`[from, to)`), тогда смежные периоды не пересекаются. Для дат в бизнес-документах часто, наоборот, обе границы включительно («с 01.09 по 30.09») — **зафиксируйте явно**.

## Деньги {#money}

::: danger Никогда не используйте float для денег
`0.1 + 0.2 = 0.30000000000000004`. Двоичная плавающая точка (`float`, `double`, `Number` в JavaScript) не представляет точно большинство десятичных дробей. Суммы накапливают ошибку, сверки расходятся на копейки.
:::

Два корректных варианта:

::: code-group

```json [Строка-десятичное]
{
  "amount": "1234.50",
  "currency": "RUB"
}
```

```json [Целое в минорных единицах]
{
  "amountMinor": 123450,
  "currency": "RUB"
}
```

```json [Google Money (units + nanos)]
{
  "currencyCode": "RUB",
  "units": "1234",
  "nanos": 500000000
}
```

:::

| | Строка-десятичное | Целое в минорных единицах |
|---|---|---|
| Читаемость | Высокая | Нужно делить на 10^n |
| Точность | Любая (можно 4 знака для курсов) | Только до минорной единицы |
| Зависимость от валюты | Нет | Число минорных единиц зависит от валюты: RUB — 2, JPY — 0, KWD — 3 |
| Риск ошибки | Клиент парсит в `double` | Перепутать рубли и копейки (ошибка в 100 раз) |
| Кто использует | PayPal, многие банковские API | Stripe, Adyen |

Правила:

- **валюта — всегда рядом с суммой**, код ISO 4217 alpha-3 (`RUB`, `USD`, `EUR`, `CNY`); цифровой код (`643`) встречается в банковских и фискальных форматах;
- число знаков после запятой — по ISO 4217 для валюты; для цен за единицу, курсов, ставок может понадобиться больше — оговорите;
- **правило округления**: математическое (half-up) или банковское (half-even), на каком шаге (по строке или по документу) — особенно для НДС и скидок;
- разделитель дробной части — точка, без разделителей разрядов (`"1234.50"`, не `"1 234,50"`);
- знак: отрицательные суммы допустимы или направление передаётся отдельным полем (`"direction": "DEBIT"`);
- если сумма числом всё же неизбежна (легаси) — в JSON это `1234.50`, и получатель обязан парсить в `BigDecimal`/`decimal`, а не в `double`.

## Числа и большие целые {#numbers}

JSON не ограничивает размер чисел, но JavaScript (и многие JSON-парсеры) хранит их как IEEE 754 `double`: целые точны только до 2^53 − 1 = `9007199254740991`.

```js
JSON.parse('{"id": 9223372036854775807}').id
// 9223372036854776000 — значение искажено без ошибки
```

- `int64` (идентификаторы, счётчики, суммы в минорных единицах больших величин) передавайте **строкой**: `"id": "9223372036854775807"`. Так делает, например, каноническое JSON-отображение Protobuf.
- В OpenAPI: `type: string, format: int64` или `type: integer, format: int64` с явным указанием в описании.
- Проценты и ставки: `"rate": "0.0725"` (доля) или `"ratePercent": "7.25"` — укажите, что именно.
- `NaN` и `Infinity` в JSON недопустимы.

## Идентификаторы {#ids}

| Вид | Пример | Плюсы | Минусы |
|---|---|---|---|
| Автоинкремент | `42` | Компактный, упорядоченный | **Раскрывает объём бизнеса** (номер заказа = число заказов), позволяет перебирать чужие объекты; конфликтует при слиянии баз и шардировании |
| UUID v4 (случайный) | `"9f1c2d3e-4a5b-4c6d-8e7f-0a1b2c3d4e5f"` | Генерируется где угодно без координации, не угадывается | 36 символов; случайный порядок → фрагментация индексов в БД |
| UUIDv7 (RFC 9562) | `"01928f3c-5d2e-7a1b-9c4d-3e5f6a7b8c9d"` | Упорядочен по времени (первые 48 бит — Unix-время в мс) — дружелюбен к индексам; совместим с типом UUID | Раскрывает время создания |
| ULID | `"01J9Z3K5V8N2Q4R6T8W0Y2A4C6"` | 26 символов Crockford Base32, сортируемый | Не стандарт IETF; нужен свой тип в БД или хранение как UUID |
| Snowflake-подобные | `"1790951400123456789"` | Упорядоченный int64 | Координация генераторов; в JSON — только строкой |
| Префиксные | `"ord_8f2k1m"`, `"cus_N3x..."` | Тип объекта виден из ID (стиль Stripe) | Свой формат |
| Естественные / внешние ключи | ИНН, номер договора, `externalId` | Бизнес-смысл, дедупликация между системами | Могут меняться, бывают неуникальны, часто содержат ПДн |

Рекомендации:

- в API идентификатор — **всегда строка**, даже если внутри число: формат можно поменять без ломающего изменения;
- клиент не должен разбирать структуру ID (идентификатор непрозрачен — opaque);
- наружу не отдавайте последовательные внутренние ID: перебор `GET /orders/1`, `/orders/2`... в сочетании с ошибками авторизации — классическая уязвимость BOLA (см. [OWASP API Top 10](/security/owasp-api));
- для новых систем хороший выбор по умолчанию — **UUIDv7** (RFC 9562, 2024, заменил RFC 4122);
- различайте **свой** ID и **внешний** ID партнёра (`externalId`), храните оба — по внешнему удобно дедуплицировать (см. [Идемпотентность](/design/idempotency)).

## Перечисления (enum) {#enum}

```json
{ "status": "PARTIALLY_PAID", "channel": "MOBILE_APP" }
```

- Значения — **строки**, не числа: `"PAID"`, а не `3`. Числовые коды нечитаемы и провоцируют ошибки сопоставления.
- Стиль: `UPPER_SNAKE_CASE` (Google AIP-126, Zalando) или `lower_snake_case` — один для всего API.
- Значения не локализуются; для отображения — справочник или отдельное поле `statusName`.
- **Расширяемость**: заранее объявите в контракте, может ли список значений расти. Клиент обязан обрабатывать неизвестное значение (маппинг в `UNKNOWN`, логирование), иначе добавление значения станет ломающим изменением (см. [Версионирование](/design/versioning)).
- Не используйте значение по умолчанию со смыслом: если поле не задано — оно отсутствует, а не `"NONE"`. Google AIP-126 рекомендует первым значением `..._UNSPECIFIED` для Protobuf.
- Большие и часто меняющиеся перечни (статусы ФНС, коды банков, категории товаров) — это **справочник**, а не enum: отдельный ресурс с версионированием.

## null, отсутствие поля и пустые значения {#null}

| Состояние | JSON | Смысл (рекомендуемое соглашение) |
|---|---|---|
| Поле отсутствует | `{}` | Значение неизвестно / не запрашивалось / в PATCH — **не менять** |
| `null` | `{"middleName": null}` | Значение явно отсутствует; в PATCH — **очистить** |
| Пустая строка | `{"middleName": ""}` | Значение — пустая строка. Обычно лучше запретить и использовать `null` |
| Пустой массив | `{"items": []}` | Список пуст |

### PATCH и три состояния

```http
PATCH /api/v1/customers/c-15 HTTP/1.1
Content-Type: application/merge-patch+json

{ "email": "new@example.com", "middleName": null }
```

По JSON Merge Patch (RFC 7396): `email` — заменить, `middleName` — удалить (очистить), остальные поля — не трогать. Из-за этого у PATCH-моделей **три** состояния поля, и генераторы кода/DTO часто не различают «отсутствует» и `null` — это нужно проверять отдельно. Альтернатива — JSON Patch (RFC 6902) с явными операциями `replace`/`remove`. См. [Методы](/http/methods).

Рекомендации:

- в ответах — единое правило: поля без значения либо всегда присутствуют со значением `null`, либо всегда опускаются. Зафиксируйте в спецификации и отразите `nullable`/`required` в схеме;
- **массивы — пустой `[]` вместо `null`**: клиенту не нужно проверять оба случая;
- булевы — без трёх состояний: если нужен «не задано», это enum (`YES`/`NO`/`UNKNOWN`), а не `true`/`false`/`null`;
- пустые строки запрещайте валидацией (`minLength: 1`), если они не несут смысла;
- `null` вместо объекта (`"address": null`) — допустимо, пустой объект `{}` — нет (неясно, что он значит).

## Булевы значения {#booleans}

- Только JSON `true`/`false`, не `"Y"`/`"N"`, `1`/`0`, `"true"`.
- Позитивные имена: `isActive`, а не `isNotBlocked` (двойные отрицания ведут к ошибкам).
- Если в будущем могут появиться третий и четвёртый варианты (статус клиента: активен/заблокирован/на проверке) — сразу делайте enum.

## Вложенность объектов {#nesting}

- Группируйте связанные поля: `"address": {...}`, `"period": {"from": ..., "to": ...}`, а не `addressCity`, `addressStreet`.
- Не более 3–4 уровней вложенности — глубже тяжело читать, валидировать и маппить.
- Связанные ресурсы — по ссылке/идентификатору (`"customerId": "c-15"`), полная вложенность — только если клиенту почти всегда нужен связанный объект (или по запросу `?expand=customer`).
- Не используйте динамические ключи (`{"2026-10-01": 5, "2026-10-02": 7}`) — их нельзя описать схемой. Лучше массив объектов: `[{"date": "2026-10-01", "count": 5}]`.

## Локализация {#localization}

| Что | Стандарт | Пример |
|---|---|---|
| Язык | BCP 47 (языковые теги на основе ISO 639) | `ru`, `ru-RU`, `en-GB`, `sr-Latn` |
| Страна | ISO 3166-1 alpha-2 | `RU`, `BY`, `KZ` |
| Регион РФ | Код субъекта (ОКАТО/КЛАДР-код региона) или ISO 3166-2 | `RU-MOW` |
| Валюта | ISO 4217 | `RUB` |

- Язык ответа запрашивается заголовком `Accept-Language: ru-RU, ru;q=0.9, en;q=0.5`, сервер сообщает его в `Content-Language` (см. [Медиатипы и согласование](/http/content-negotiation)).
- Многоязычные значения в данных: `"name": {"ru": "Молоко", "en": "Milk"}` или отдельные ресурсы переводов.
- Форматирование чисел, дат, валют для отображения — задача клиента; в API — только машинные форматы.

## Контактные данные {#contacts}

### Телефоны

- Формат **E.164**: `+` и до 15 цифр, без пробелов, скобок и дефисов: `"+79161234567"`.
- Не передавайте телефон числом — потеряется `+` и ведущие нули.
- Российские номера: `8 916 ...` и `+7 916 ...` — один и тот же номер; нормализуйте к E.164 на входе.
- Добавочный номер — отдельным полем (`"extension": "123"`).

### Email

- Строка; для валидации — `format: email` в JSON Schema или простая проверка (полная грамматика RFC 5322 сложна и редко нужна).
- Доменная часть нечувствительна к регистру, локальная часть формально чувствительна — для сравнения обычно приводят к нижнему регистру, но **храните как ввёл пользователь**.
- Подтверждённость адреса — отдельный флаг (`isEmailVerified`).

### Адреса

- Структурированный адрес лучше строки: `country`, `region`, `city`, `street`, `house`, `flat`, `postalCode`, плюс строковое `fullAddress` для отображения.
- В России для однозначной идентификации адресов используется **ГАР** (Государственный адресный реестр), ведётся в ФИАС (федеральная информационная адресная система); устаревший формат — КЛАДР. Передавайте идентификатор объекта ГАР (GUID) вместе с текстом — это позволяет сопоставлять адреса между системами. Для нормализации ввода часто используют сервисы подсказок.
- Почтовый индекс — строка (`"010000"` в Казахстане, ведущие нули встречаются).

## Российские реквизиты {#ru-requisites}

::: danger Реквизиты — только строками
ИНН Республики Башкортостан начинается с `02`: число `0274062111` превратится в `274062111`, и ИНН станет невалидным. Это касается всех кодов с ведущими нулями. Кроме того, это **идентификаторы**, а не числа: над ними не выполняют арифметику.
:::

| Реквизит | Формат | Пример | Особенности |
|---|---|---|---|
| ИНН юрлица | 10 цифр | `"7707083893"` | Контрольная цифра |
| ИНН физлица / ИП | 12 цифр | `"500100732259"` | Две контрольные цифры |
| КПП | 9 символов | `"770701001"` | Символы 5–6 могут быть заглавными латинскими буквами — не валидируйте как «только цифры» |
| ОГРН | 13 цифр | `"1027700132195"` | Контрольная цифра |
| ОГРНИП | 15 цифр | `"304500116000157"` | |
| БИК | 9 цифр | `"044525225"` | Начинается с `04` |
| Расчётный / корр. счёт | 20 цифр | `"40702810938000000001"` | Контрольный ключ вместе с БИК; превышает int64 — только строка |
| СНИЛС | 11 цифр | `"11223344595"` | Храните без разделителей, форматируйте при отображении (`112-233-445 95`) |
| ОКПО | 8 (юрлица) или 10 (ИП) цифр | `"00032537"` | Ведущие нули |
| ОКТМО | 8 или 11 цифр | `"45000000"` | |
| Паспорт РФ | Серия 4 цифры + номер 6 цифр | `{"series": "4509", "number": "123456"}` | ПДн, раздельные поля |

- Валидируйте длину и контрольные суммы на входе — это ловит опечатки до того, как данные уйдут в смежные системы.
- Пустой КПП у ИП — отсутствие поля или `null`, а не `"0"` или `"000000000"`.

## Персональные данные {#pii}

Обработка ПДн регулируется 152-ФЗ (и GDPR для европейских субъектов). Для API это означает:

- **минимизация**: отдавайте только поля, нужные потребителю для его задачи;
- **маскирование** в ответах, где полное значение не нужно: `"phone": "+7916***4567"`, `"cardNumber": "220220******1234"`, `"passportNumber": "****56"`;
- маскирование в **логах** и сообщениях об ошибках (см. [Ошибки](/design/errors));
- ПДн не передаются в URI (query-параметры попадают в логи прокси и историю): поиск по телефону — `POST /customers/search`, а не `GET /customers?phone=...`;
- номера карт — требования PCI DSS: полный PAN только в защищённом контуре, наружу — маскированный или токен;
- в спецификации помечайте поля с ПДн (например, расширением `x-pii: true` в OpenAPI) — это помогает настроить маскирование и аудит.

## Версия схемы в данных {#schema-version}

Для хранимых и пересылаемых документов (события, файлы выгрузок, сообщения в брокере) полезно включать версию схемы прямо в данные:

```json
{
  "schemaVersion": "2.1",
  "eventType": "order.created",
  "data": { "orderId": "ord-501" }
}
```

Для синхронного REST версия обычно определяется версией API (см. [Версионирование](/design/versioning)), а для событий — версией схемы в реестре.

## Типичные ошибки {#mistakes}

- Дата-время без часового пояса; дата рождения как полночь UTC.
- Сумма во `float`/`double`; сумма без валюты; неясно, рубли или копейки.
- `int64` числом в JSON — искажение в JavaScript без единой ошибки.
- ИНН, БИК, счёт, индекс числом — потеря ведущих нулей.
- Числовые enum (`"status": 3`) и enum без правила для неизвестных значений.
- Смешение стилей именования (`customerId` и `order_date` в одном ответе).
- `null` вместо пустого массива; `"Y"`/`"N"` вместо булевых.
- PATCH-обработчик не различает «поле не передано» и `null` — данные затираются.
- Последовательные ID наружу — перебор объектов.
- Телефоны в произвольном формате (`8 (916) 123-45-67`).
- ПДн в query-параметрах и логах.

## На что обратить внимание аналитику {#checklist}

- [ ] Зафиксирован стиль именования полей и enum-значений.
- [ ] Формат дат-времени: RFC 3339, обязательное смещение, правило UTC; даты без времени — `full-date`.
- [ ] Часовые пояса — IANA; определено, где они нужны (расписания, местное время).
- [ ] Длительности и периоды: формат, включительность границ.
- [ ] Деньги: формат суммы, валюта ISO 4217, точность, правило и шаг округления.
- [ ] Большие целые и идентификаторы — строками.
- [ ] Тип идентификаторов (UUIDv7, ULID и т. п.), различие внутренних и внешних ID, ID не последовательные.
- [ ] Перечисления: перечень значений, расширяемость, обработка неизвестных значений.
- [ ] Правила для `null`, отсутствующих полей, пустых строк и массивов; семантика PATCH.
- [ ] Языки, страны, телефоны, email, адреса — стандарты и нормализация.
- [ ] Российские реквизиты — строками, с проверкой длины и контрольных сумм.
- [ ] Перечислены поля с ПДн, правила маскирования, запрет ПДн в URI и логах.
- [ ] Все соглашения отражены в схеме OpenAPI (`format`, `pattern`, `nullable`, `required`, `example`).
