# Фильтрация, сортировка, поиск и выбор полей

Как клиенту сказать «дай оплаченные заказы клиента 5 за май, отсортированные по сумме, только id и сумму». Для этого нет единого стандарта HTTP — есть несколько устоявшихся стилей. Задача аналитика — выбрать один, описать его точно и применять одинаково во всём API.

::: info Где это в стандартах
RFC 3986 определяет только синтаксис query-строки. Семантику параметров каждое API задаёт само. Готовые соглашения: [OData](/protocols/odata) (`$filter`, `$orderby`, `$select`, `$expand`), JSON:API, Google AIP-160, RSQL/FIQL. Как раскладывать параметры между path, query, header и body — см. [Ресурсы и URI](/design/).
:::

## Простые фильтры

Параметр с именем поля и значением — равенство. Несколько параметров объединяются по **И**.

```http
GET /v1/orders?status=PAID&customerId=5 HTTP/1.1
```

Правила:

- Имя параметра совпадает с именем поля в ответе (`customerId` в фильтре — `customerId` в JSON), в том же стиле — camelCase или snake_case.
- Значения перечислений — в том же регистре, что и в ответе (`PAID`, а не `paid`), либо явно оговорите регистронезависимость.
- Неизвестный параметр: либо игнорировать (гибко, но опечатка `?stauts=PAID` молча вернёт всё), либо `400 Bad Request`. Для интеграций безопаснее **отклонять** неизвестные фильтры.

## Несколько значений одного поля

| Стиль | Пример | Плюсы | Минусы |
|---|---|---|---|
| Через запятую | `?status=PAID,SHIPPED` | Компактно, легко читать | Значение не может содержать запятую без экранирования |
| Повтор параметра | `?status=PAID&status=SHIPPED` | Значения любые, стандартно для форм | Длиннее, часть фреймворков берёт только первое значение |
| Со скобками | `?status[]=PAID&status[]=SHIPPED` | Привычно для PHP и Rails | Скобки нужно кодировать (`%5B%5D`), нестандартно |
| Оператор `in` | `?status=in:PAID,SHIPPED` | Явный оператор | Нужен парсер операторов |

::: tip Как описать в OpenAPI
Для массивов в query OpenAPI по умолчанию использует `style: form, explode: true` — это повтор параметра (`?status=PAID&status=SHIPPED`). Через запятую — `style: form, explode: false`. Укажите стиль явно, иначе генераторы клиентов и сервер поймут параметр по-разному. См. [OpenAPI](/specs/openapi).
:::

Значения внутри одного поля объединяются по **ИЛИ**, разные поля — по **И**: `?status=PAID,SHIPPED&customerId=5` означает «(оплачен ИЛИ отгружен) И клиент 5».

## Диапазоны

| Стиль | Пример |
|---|---|
| Пара параметров с суффиксами | `?createdFrom=2024-05-01T00:00:00Z&createdTo=2024-06-01T00:00:00Z` |
| Суффикс оператора | `?created_gte=2024-05-01&created_lt=2024-06-01` |
| LHS brackets (оператор в имени) | `?created[gte]=2024-05-01&created[lt]=2024-06-01` (так у Stripe) |
| RHS colon (оператор в значении) | `?created=gte:2024-05-01&total=gt:1000` |

::: warning Границы диапазона
Явно опишите, включаются ли границы. Рекомендация — **полуоткрытый интервал**: `from` включительно, `to` не включительно. Тогда соседние периоды не пересекаются и не теряют записи: `createdFrom=2024-05-01T00:00:00Z&createdTo=2024-06-01T00:00:00Z` — ровно май. Вариант «по `2024-05-31` включительно» с датой без времени потеряет всё, что создано 31 мая после полуночи. Также укажите часовой пояс — см. [Соглашения о данных](/design/data-conventions).
:::

## Операторы

| Оператор | Значение | LHS brackets | RHS colon | Суффикс |
|---|---|---|---|---|
| `eq` | равно | `status[eq]=PAID` | `status=eq:PAID` | `status=PAID` |
| `ne` | не равно | `status[ne]=NEW` | `status=ne:NEW` | `status_ne=NEW` |
| `gt`, `gte` | больше, больше или равно | `total[gte]=100` | `total=gte:100` | `total_gte=100` |
| `lt`, `lte` | меньше, меньше или равно | `total[lt]=500` | `total=lt:500` | `total_lt=500` |
| `in` | одно из | `status[in]=PAID,SHIPPED` | `status=in:PAID,SHIPPED` | `status_in=PAID,SHIPPED` |
| `like`, `contains` | подстрока | `name[contains]=ООО` | `name=contains:ООО` | `name_contains=ООО` |
| `exists`, `isNull` | наличие значения | `deliveredAt[exists]=false` | `deliveredAt=isnull:` | `deliveredAt_isNull=true` |

Сравнение стилей:

- **LHS brackets** — читаемо, имя поля отдельно от оператора, легко валидировать по белому списку. Скобки в URL нужно кодировать (многие клиенты делают это сами).
- **RHS colon** — не нужны скобки, но значение с двоеточием (время `10:00`) неоднозначно: требуется правило «оператор — до первого двоеточия».
- **Суффиксы** — просты для любых клиентов, но имена параметров множатся.

::: warning Фильтр по null
Решите, как выразить «поле пустое»: `?deliveredAt=null` неоднозначен (строка `"null"` или отсутствие значения). Используйте явный оператор (`deliveredAt[exists]=false`) или отдельный булев параметр (`?isDelivered=false`).
:::

## Языки запросов

Когда простых фильтров мало (нужны ИЛИ между разными полями, скобки, отрицания), используют язык выражений в одном параметре.

::: code-group

```http [RSQL / FIQL]
GET /v1/orders?filter=status=in=(PAID,SHIPPED);total=gt=1000 HTTP/1.1
```

```http [OData]
GET /v1/orders?$filter=Status eq 'Paid' and Total gt 1000&$orderby=CreatedAt desc HTTP/1.1
```

```http [Google AIP-160]
GET /v1/orders?filter=status = "PAID" AND total > 1000 HTTP/1.1
```

:::

Запросы показаны без процентного кодирования для читаемости — в реальном URL пробелы, кавычки и спецсимволы кодируются.

| Язык | Синтаксис | Плюсы | Минусы |
|---|---|---|---|
| **RSQL / FIQL** | `==`, `!=`, `=gt=`, `=in=`; `;` — И, `,` — ИЛИ | Компактен, URL-дружелюбен, есть библиотеки для Java/JS | Неочевиден непосвящённым |
| **OData** `$filter` | `eq`, `ne`, `gt`, `and`, `or`, функции `contains`, `startswith` | Стандарт OASIS, мощный, поддержка в экосистеме Microsoft, SAP | Тяжёл в реализации, легко дать клиенту слишком много власти |
| **Google AIP-160** | `=`, `!=`, `>`, `AND`, `OR`, `NOT`, `:` (has) | Читаем, описан формально | Нужен собственный парсер |
| **Собственный** | Любой | Под задачу | Придётся документировать и поддерживать грамматику |

Подробнее про OData — [OData](/protocols/odata). Если клиентам действительно нужны произвольные запросы с выбором полей и связей — возможно, правильнее [GraphQL](/protocols/graphql).

## Полнотекстовый поиск

```http
GET /v1/customers?q=иванов москва&limit=20 HTTP/1.1
```

- Параметр `q` (или `search`, `$search` в OData) — свободный текст; сервер сам решает, по каким полям искать.
- Опишите: по каким полям идёт поиск, учитывается ли морфология, регистр, ё/е, опечатки, минимальная длина запроса (например, от 3 символов), порядок результатов (по релевантности), можно ли сочетать с фильтрами.
- Поиск `LIKE '%текст%'` по большой таблице без полнотекстового индекса — полное сканирование. Нагрузку от такого поиска нужно оценить заранее.

## Сортировка

```http
GET /v1/orders?sort=-createdAt,customerName HTTP/1.1
```

| Стиль | Пример | Кто использует |
|---|---|---|
| Минус — по убыванию | `sort=-createdAt,name` | JSON:API, Zalando |
| Суффикс направления | `sort=createdAt:desc,name:asc` | Многие REST API |
| Отдельные параметры | `sortBy=createdAt&sortOrder=desc` | Простые API, одно поле |
| SQL-подобный | `orderBy=createdAt desc, name` | Google AIP-132, OData `$orderby` |

Правила:

- Сортировка по умолчанию задокументирована и **стабильна**: сервер добавляет уникальный ключ (`id`) последним — иначе [пагинация](/design/pagination) даёт дубли и пропуски.
- Сортировать можно только по полям из **белого списка** и только по проиндексированным.
- Описать, где окажутся `null` (в начале или в конце) и как сравниваются строки (регистр, локаль — `ё` после `е` или после `я`).

## Выбор полей (sparse fieldsets)

Клиент запрашивает только нужные поля — меньше трафика, быстрее сериализация.

::: code-group

```http [Простой стиль]
GET /v1/orders/42?fields=id,status,total,customer.name HTTP/1.1

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "42", "status": "PAID", "total": "3000.00", "customer": { "name": "ООО Ромашка" } }
```

```http [JSON:API]
GET /v1/orders?fields[orders]=status,total&fields[customers]=name&include=customer HTTP/1.1
```

```http [OData]
GET /v1/Orders?$select=Id,Status,Total HTTP/1.1
```

:::

- Опишите, всегда ли возвращается `id` (рекомендуется — да) и что происходит с неизвестным полем (`400` или игнор).
- Вложенные поля — через точку (`customer.name`) или по типам (JSON:API).
- Альтернатива — предопределённые представления: `?view=summary` / `?view=full` (Google AIP-157 описывает оба подхода).

## Включение связанных ресурсов (expand / include)

```http
GET /v1/orders/42?expand=customer,items.product HTTP/1.1
```

```json
{
  "id": "42",
  "customer": { "id": "7", "name": "ООО Ромашка" },
  "items": [
    { "sku": "SKU-001", "quantity": 2, "product": { "id": "p1", "name": "Кабель" } }
  ]
}
```

Без `expand` поле `customer` содержит только ссылку или ID (`"customerId": "7"`). Ограничения, которые нужно прописать: допустимые связи (белый список), максимальная глубина (обычно 1–2), влияние на [rate limiting](/design/rate-limiting) и время ответа. В JSON:API связанные ресурсы отдаются отдельным массивом `included`, в OData — `$expand`, у Stripe — `expand[]=customer`.

## POST /search и метод QUERY {#post-search}

Когда фильтр не помещается в URL, содержит персональные данные или имеет сложную структуру:

```http
POST /v1/orders/search HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "filter": {
    "and": [
      { "field": "status", "op": "in", "value": ["PAID", "SHIPPED"] },
      { "or": [
        { "field": "total", "op": "gte", "value": "100000" },
        { "field": "customer.inn", "op": "eq", "value": "7707083893" }
      ]}
    ]
  },
  "sort": [ { "field": "createdAt", "direction": "desc" } ],
  "fields": ["id", "status", "total"],
  "limit": 50,
  "cursor": null
}
```

Ответ — `200 OK` с той же структурой, что у `GET /v1/orders`. Минусы `POST`: формально небезопасен и неидемпотентен, не кэшируется, клиенты и gateway не повторяют его автоматически — в документации укажите, что `/search` безопасен и его можно повторять.

::: info Метод QUERY
IETF стандартизует новый метод `QUERY` (черновик `draft-ietf-httpbis-safe-method-w-body`): безопасный и идемпотентный, как `GET`, но с телом, как `POST`. Ответ на него может кэшироваться с учётом тела. Перед использованием проверьте статус документа и поддержку метода в вашем gateway, WAF, балансировщике, клиентских библиотеках и генераторе OpenAPI — пока это редкость.
:::

## Кодирование значений в URL

Значения query-параметров кодируются процентным кодированием (percent-encoding, RFC 3986) в UTF-8.

| Символ | Кодирование | Зачем |
|---|---|---|
| пробел | `%20` (или `+` в формате `application/x-www-form-urlencoded`) | Разделитель |
| `&` | `%26` | Иначе начнётся новый параметр: `?name=Иванов & сын` |
| `=` | `%3D` | Разделитель имени и значения |
| `+` | `%2B` | **Иначе превратится в пробел** |
| `#` | `%23` | Иначе отрежется как фрагмент |
| `,` | `%2C` | Если запятая — разделитель списка |
| Кириллица | `%D0%98...` | UTF-8 байты |

::: danger Ловушка с часовым поясом
`?createdFrom=2024-05-01T00:00:00+03:00` — сервер получит `2024-05-01T00:00:00 03:00` (плюс стал пробелом) и вернёт `400` или, хуже, неверный результат. Кодируйте `+` как `%2B` или передавайте время в UTC с `Z`.
:::

## Длина URL

- RFC 9110 рекомендует поддерживать URI длиной **не менее 8000 октетов**; жёсткого ограничения в стандарте нет.
- На практике ограничивают браузеры, прокси, балансировщики, WAF и веб-серверы — часто 4–8 КБ на строку запроса или заголовки. При превышении — [`414 URI Too Long`](/http/status-codes#414) (или `400`, `431` от промежуточных узлов).
- Если фильтр может содержать сотни ID (`?id=1,2,3,...`) — сразу проектируйте [`POST /search`](#post-search).

## Безопасность и производительность

::: danger Опасно
- **Инъекции.** Значения фильтров никогда не подставляются в SQL строкой — только параметризованные запросы. Имена полей и направление сортировки нельзя параметризовать в SQL, поэтому они проверяются по **белому списку** и маппятся на колонки.
- **Обход прав доступа.** Фильтр — это не авторизация. `?customerId=8` от клиента 7 должен вернуть пустой список или `403`, а не чужие заказы. Ограничения доступа сервер накладывает сам, поверх клиентских фильтров. См. [OWASP API Top 10](/security/owasp-api).
- **Отказ в обслуживании.** Фильтр по неиндексированному полю, `contains` с ведущим подстановочным символом, сортировка большого результата без индекса, глубокий `expand`, регулярные выражения от клиента — всё это может положить базу.
:::

Защитные меры:

- белый список полей для фильтрации, сортировки, `fields` и `expand`;
- фильтрация и сортировка только по проиндексированным полям, либо обязательный узкий фильтр (например, период не более 31 дня);
- ограничение сложности выражений: число условий, глубина вложенности, длина строки;
- таймаут запроса к БД и [rate limiting](/design/rate-limiting);
- в языке запросов — запрет на функции, которые не нужны клиентам.

## Сводная таблица стилей

| Задача | Простой стиль (рекомендуется для большинства API) | JSON:API | OData | Google AIP |
|---|---|---|---|---|
| Равенство | `status=PAID` | `filter[status]=PAID` | `$filter=Status eq 'PAID'` | `filter=status = "PAID"` |
| Диапазон | `createdFrom=...&createdTo=...` | `filter[...]` (не стандартизовано) | `$filter=Created ge ... and Created lt ...` | `filter=create_time >= "..."` |
| Сортировка | `sort=-createdAt` | `sort=-createdAt` | `$orderby=CreatedAt desc` | `order_by=create_time desc` |
| Выбор полей | `fields=id,total` | `fields[orders]=id,total` | `$select=Id,Total` | `read_mask` / `$fields` |
| Связанные | `expand=customer` | `include=customer` | `$expand=Customer` | — |
| Поиск | `q=текст` | не стандартизовано | `$search=текст` | — |
| Пагинация | `limit`, `cursor` | `page[...]` | `$top`, `$skip` | `page_size`, `page_token` |

## Рекомендации по единообразию

1. Один стиль фильтров, сортировки, выбора полей и пагинации — для **всех** ресурсов API. Опишите его один раз в общем разделе гайдлайна, в ресурсах указывайте только списки разрешённых полей.
2. Имена параметров = имена полей в ответе.
3. Одинаковые суффиксы диапазонов везде (`...From`/`...To` или `[gte]`/`[lt]`).
4. Даты и время — в одном формате (ISO 8601 / RFC 3339) с часовым поясом.
5. Неизвестные параметры и поля — одинаковая реакция (`400` с указанием параметра).
6. Сложные запросы — через единый `POST /{resource}/search` с одной схемой тела.

## Типичные ошибки

- Фильтр, молча игнорирующий опечатку в имени параметра, — клиент получает все данные.
- Даты без часового пояса и неописанные границы диапазона.
- Нераскодированный `+` в смещении часового пояса.
- Сортировка по любому полю без индекса.
- Фильтр, через который можно получить чужие данные.
- Персональные данные в query (`?phone=`, `?passport=`) — оседают в логах.
- Разные стили в разных ресурсах (`status=PAID,NEW` и `state[]=PAID&state[]=NEW`).
- Строковая сборка SQL из параметров запроса.

## На что обратить внимание аналитику

- [ ] Для каждого списочного ресурса перечислены поля фильтрации, операторы и типы значений.
- [ ] Описан стиль множественных значений и диапазонов, границы (включительно или нет), часовой пояс.
- [ ] Для сортировки — разрешённые поля, сортировка по умолчанию, порядок `null`, уникальный tie-breaker.
- [ ] Для `fields`/`expand` — разрешённые поля и связи, максимальная глубина.
- [ ] Для `q` — поля поиска, минимальная длина, учёт регистра и морфологии.
- [ ] Определена реакция на неизвестные и некорректные параметры (`400` с деталями).
- [ ] Проверено, что все фильтруемые и сортируемые поля имеют индексы или есть обязательные ограничивающие фильтры.
- [ ] Ограничения доступа накладываются сервером независимо от фильтров клиента.
- [ ] Персональные данные не передаются в query; для них — `POST /search`.
- [ ] Учтены лимиты длины URL и описан `POST /search` для длинных запросов.
- [ ] Стиль параметров массивов явно указан в [OpenAPI](/specs/openapi) (`style`, `explode`).
