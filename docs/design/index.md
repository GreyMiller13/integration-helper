# Ресурсы и URI

Как назвать эндпоинты, как выстроить иерархию, куда положить параметр — в путь, query, заголовок или тело — и что делать с операциями, которые не укладываются в CRUD. От этих решений зависит, будет ли API понятным, единообразным и пригодным к развитию без ломающих изменений.

::: info Где это в стандартах
Синтаксис URI задаёт RFC 3986, семантику методов — RFC 9110. Сам стиль REST описан в диссертации Роя Филдинга. Правила нейминга, вложенности и регистра — это **соглашения**, а не стандарт: их фиксируют в гайдлайнах компании (Google AIP, Microsoft, Zalando — ссылки в конце страницы). Основы стиля — на странице [REST](/protocols/rest), методы — в разделе [Методы HTTP](/http/methods).
:::

## Принципы проектирования

| Принцип | Что означает на практике |
|---|---|
| **Ресурсо-ориентированность** | API описывает **сущности** (заказы, клиенты, платежи), а не процедуры. URI — существительное, действие выражается HTTP-методом |
| **Единый интерфейс** | Одни и те же методы, коды, форматы ошибок, пагинация и фильтрация во всех ресурсах. Освоив один эндпоинт, потребитель понимает остальные |
| **API-first (contract-first)** | Сначала контракт ([OpenAPI](/specs/openapi)), его согласование с потребителями, затем реализация и моки. Контракт — источник правды |
| **Предсказуемость** | Одинаковые имена полей для одинаковых понятий (`createdAt` везде, а не `created`, `creationDate`, `dt_create`) |
| **Минимальная связанность** | URI и модель ресурса не повторяют структуру таблиц БД и внутренних сервисов. Внутренний рефакторинг не должен ломать API |
| **Эволюционируемость** | Добавление полей и ресурсов не ломает клиентов. Подробнее — [Версионирование](/design/versioning) |
| **Безопасность по умолчанию** | Идентификаторы не раскрывают лишнего, чувствительные данные не попадают в URL (они оседают в логах прокси и истории браузера) |

## Анатомия URI

```text
https://api.example.com/v1/customers/42/orders?status=paid&limit=20#top
\___/   \_____________/\_/\___________________/\_____________________/
схема        хост     версия      путь                 query
```

- **Путь** (path) идентифицирует ресурс: коллекцию или элемент.
- **Query** уточняет выборку или представление: фильтр, сортировка, пагинация, набор полей.
- **Фрагмент** (`#...`) на сервер не отправляется — в API не используется.

## Нейминг ресурсов {#naming}

### Существительные во множественном числе

Коллекция называется существительным во множественном числе, элемент — коллекция плюс идентификатор:

```text
GET  /orders          — коллекция заказов
GET  /orders/42       — заказ 42
POST /orders          — создать заказ в коллекции
```

Единственное число (`/order/42`) встречается, но смешивать стили нельзя. Множественное число — выбор большинства гайдлайнов (Google, Microsoft, Zalando).

### Регистр и разделители в пути

| Вариант | Пример | Комментарий |
|---|---|---|
| **kebab-case** | `/sales-orders/42/line-items` | Рекомендуется: читаемо, не зависит от регистра, принят у Zalando, Microsoft |
| camelCase | `/salesOrders/42/lineItems` | Встречается (Google AIP для коллекций), но путь чувствителен к регистру — легко ошибиться |
| snake_case | `/sales_orders/42` | Допустимо, но подчёркивание теряется при подчёркнутом отображении ссылок |
| UPPER / смешанный | `/SalesOrders` | Не использовать |

::: warning Путь чувствителен к регистру
По RFC 3986 регистронезависимы только схема и хост. `/Orders` и `/orders` — **разные** URI. Договоритесь о нижнем регистре и не полагайтесь на то, что сервер «поймёт». Значения идентификаторов (`/orders/AB-12`) регистр сохраняют.
:::

### Имена полей в JSON: camelCase или snake_case

Стандарта нет — важно **выбрать один стиль и соблюдать его во всём API**, включая query-параметры (`?customerId=` при camelCase в теле).

| Стиль | Кто использует | Плюсы |
|---|---|---|
| `camelCase` | Microsoft, Google JSON-представление, большинство JS/Java-стеков | Естественно для JavaScript, Java, C#; без маппинга |
| `snake_case` | Zalando, Stripe, GitHub, Twitter | Читаемо, естественно для Python, Ruby, SQL |

::: tip Совет
Зафиксируйте стиль в гайдлайне и в линтере контракта (например, Spectral для OpenAPI). Аббревиатуры пишите как слово: `orderId`, `httpCode`, `vatAmount` — а не `orderID`, `HTTPCode`.
:::

### Чего избегать в именах

- **Глаголы в пути**: `/getOrders`, `/createOrder`, `/orders/delete/42`. Действие задаёт метод.
- **Расширения файлов**: `/orders/42.json`. Формат согласуется через `Accept` и `Content-Type` — см. [Медиатипы и согласование](/http/content-negotiation). Исключение — реальные файлы (`/reports/2024-q1.pdf` в файловом хранилище).
- **Технические детали**: `/api/OrderService.svc/`, `/servlet/`, `/v1/db/tbl_orders`.
- **Трейлинг-слэш**: `/orders/` и `/orders` по RFC 3986 — разные URI. Выберите вариант без слэша; со слэшем — либо `301`/`308` на канонический путь, либо `404`, но поведение должно быть описано. Редирект для `POST` опасен: часть клиентов при `301` меняет метод на `GET` — используйте `308 Permanent Redirect` или просто не поддерживайте слэш.
- **Сокращения**: `/cstmrs`, `/ord`. Пишите полные слова.

## Коллекции и элементы

| Запрос | Смысл | Успешный ответ |
|---|---|---|
| `GET /orders` | Список (с [пагинацией](/design/pagination) и [фильтрацией](/design/filtering)) | `200 OK` |
| `POST /orders` | Создать элемент, идентификатор назначает сервер | `201 Created` + `Location` |
| `GET /orders/42` | Получить элемент | `200 OK` / `404 Not Found` |
| `PUT /orders/42` | Полная замена (или создание, если клиент назначает ID) | `200 OK` / `204 No Content` / `201 Created` |
| `PATCH /orders/42` | Частичное изменение | `200 OK` / `204 No Content` |
| `DELETE /orders/42` | Удаление | `204 No Content` / `200 OK` / `202 Accepted` |
| `DELETE /orders` | Удалить всю коллекцию | Обычно **не поддерживается** — `405 Method Not Allowed` |

## Иерархия и вложенность

Вложенный путь выражает **отношение владения**: элемент не существует без родителя.

```text
GET /orders/42/items          — позиции заказа 42
GET /orders/42/items/3        — позиция 3 заказа 42
```

Правила:

1. **Не глубже двух уровней** «коллекция/элемент»: `/customers/7/orders` — нормально, `/customers/7/orders/42/items/3/discounts` — нет.
2. Если у сущности есть глобально уникальный ID, давайте к ней **прямой путь**: `/orders/42`, а не только `/customers/7/orders/42`.
3. Связь «многие ко многим» или слабая связь — через фильтр, а не вложенность: `GET /orders?customerId=7`.
4. Не дублируйте один ресурс под несколькими путями без нужды — получите расхождения в правах доступа и кэшировании.

::: details Как решить: вложенность или фильтр
- Дочерний объект живёт и удаляется вместе с родителем (позиции заказа, адреса клиента) → вложенный ресурс.
- Объект самостоятелен, у него свой жизненный цикл (заказы клиента, платежи по заказу) → свой корневой ресурс `/payments` и фильтр `?orderId=42`. Вложенный путь `/orders/42/payments` допустим как удобный «срез» только для чтения.
:::

## Синглтоны (singleton resources)

Ресурс, который существует в единственном экземпляре в контексте родителя, — без идентификатора:

```text
GET   /users/me                    — текущий пользователь (из токена)
GET   /orders/42/delivery          — доставка заказа (одна на заказ)
PUT   /customers/7/settings        — настройки клиента
GET   /system/health               — состояние сервиса
```

Синглтон обычно нельзя создать `POST` или удалить `DELETE` — он есть всегда; используются `GET`, `PUT`, `PATCH`.

::: warning /me и безопасность
`/users/me` удобен: клиенту не нужно знать свой ID, а сервер берёт его из токена. Но если наряду с ним есть `/users/{id}`, сервер **обязан** проверять, что вызывающий имеет право читать чужой ID. Иначе — уязвимость BOLA, см. [OWASP API Top 10](/security/owasp-api).
:::

## Действия, которые не ложатся на CRUD {#actions}

Отмена заказа, проведение платежа, отправка письма, пересчёт цен — это переходы состояния или процедуры. Три основных варианта:

::: code-group

```http [Действие-подресурс]
POST /orders/42/cancel HTTP/1.1
Content-Type: application/json

{ "reason": "CUSTOMER_REQUEST" }
```

```http [PATCH статуса]
PATCH /orders/42 HTTP/1.1
Content-Type: application/merge-patch+json

{ "status": "CANCELLED", "cancelReason": "CUSTOMER_REQUEST" }
```

```http [Ресурс-событие]
POST /orders/42/cancellations HTTP/1.1
Content-Type: application/json

{ "reason": "CUSTOMER_REQUEST" }
```

:::

| Вариант | Плюсы | Минусы | Когда применять |
|---|---|---|---|
| **Действие** `POST /orders/42/cancel` (у Google — `POST /orders/42:cancel`) | Явная бизнес-операция, легко описать права и валидацию, понятна аналитику и потребителю | Глагол в URI — отступление от «чистого» REST; `POST` не идемпотентен | Операция с побочными эффектами (возврат денег, уведомления), сложными правилами перехода |
| **PATCH статуса** | «Чистый» REST, один эндпоинт | Бизнес-логика прячется за изменением поля; сложно разграничить права (менять адрес можно, а статус — нет); неясно, какие переходы разрешены | Простые статусы без побочных эффектов |
| **Ресурс-событие** `POST /orders/42/cancellations` | REST-совместимо, у отмены появляется свой ID и история (`GET /orders/42/cancellations`) | Искусственная сущность, если история не нужна | Когда у действия есть собственные данные и аудит: возвраты (`/refunds`), платежи, согласования |

::: tip Рекомендация
Для значимых бизнес-операций используйте **действие-подресурс** или **ресурс-событие**, а не `PATCH status`. Опишите в постановке матрицу допустимых переходов состояния и ответ на недопустимый переход — обычно [`409 Conflict`](/http/status-codes#409) (заказ уже отгружен) или [`422 Unprocessable Content`](/http/status-codes#422). Сделайте действие [идемпотентным](/design/idempotency): повторная отмена уже отменённого заказа — успех, а не ошибка.
:::

## Поиск: GET с query или POST /search

| | `GET /orders?status=paid&from=2024-01-01` | `POST /orders/search` |
|---|---|---|
| Семантика | Безопасный и идемпотентный запрос | `POST` формально небезопасен и неидемпотентен |
| [Кэширование](/design/caching) | Работает «из коробки» | Не кэшируется прокси и CDN |
| Закладки, логи, отладка | URL самодостаточен | Нужно тело |
| Длина и сложность | Ограничена длиной URL (практически 2–8 КБ) | Без ограничений, вложенные условия OR/AND |
| Чувствительные данные | Попадают в логи и историю | Остаются в теле |

Правило: простой поиск — `GET` с query-параметрами; сложные фильтры, длинные списки ID или персональные данные в критериях (ИНН, телефон, паспорт) — `POST /orders/search` (`200 OK` с результатами, тело описано в контракте). Готовится стандартный безопасный метод с телом — `QUERY`. Подробнее — [Фильтрация и сортировка](/design/filtering).

## Идентификаторы в URI

| Тип ID | Пример | Плюсы | Минусы |
|---|---|---|---|
| Автоинкремент | `/orders/1042` | Короткий, читаемый | Раскрывает объём бизнеса, легко перебрать, конфликтует при слиянии баз |
| UUID (v4, v7) | `/orders/3f2b9c1e-...` | Глобально уникален, генерируется клиентом, не перебирается. UUIDv7 сортируем по времени | Длинный, неудобен для людей |
| Бизнес-ключ | `/orders/SO-2024-000123` | Понятен людям, совпадает с учётной системой | Может меняться, может содержать спецсимволы (`/`, пробел) — нужно кодирование |
| Составной | `/warehouses/MSK/items/A-17` | Отражает естественную модель | Сложнее в ссылках и фильтрах |

::: warning Внимание
- ID в пути — **непрозрачная строка** для клиента: не стройте логику на его формате.
- Не используйте в пути персональные данные (email, телефон, номер паспорта): URL логируется на всех узлах. Для поиска по ним — `POST /search` или поиск по хэшу.
- Если бизнес-ключ может содержать `/`, `?`, `#`, `%`, пробел — значения кодируются (`%2F`), но часть прокси и фреймворков декодирует `%2F` неправильно. Надёжнее не допускать таких символов в ключах пути.
- Подробнее о форматах идентификаторов — [Соглашения о данных](/design/data-conventions).
:::

## Что куда класть: path, query, header, body {#where-to-put}

| Место | Для чего | Примеры | Не класть |
|---|---|---|---|
| **Path** | Идентификация ресурса | `/orders/42`, `/customers/7/addresses` | Фильтры, флаги, персональные данные |
| **Query** | Уточнение выборки и представления | `?status=paid`, `?sort=-createdAt`, `?limit=50`, `?fields=id,total`, `?expand=customer` | Секреты, токены, ПДн, большие объёмы |
| **Header** | Метаданные запроса, сквозные параметры | `Authorization`, `Accept`, `Accept-Language`, `If-Match`, `Idempotency-Key`, `X-Request-Id`, `traceparent`, `Prefer` | Бизнес-данные сущности |
| **Body** | Состояние ресурса, параметры операции | JSON создаваемого заказа, параметры отмены, сложный поисковый запрос | Для `GET`/`DELETE` тело не используется — его семантика не определена, многие прокси его отбрасывают |

::: danger Опасно
Токены и ключи API — **только в заголовках** (`Authorization`). Query-строка попадает в логи веб-серверов, балансировщиков, `Referer` и историю браузера. См. [Аутентификация](/security/authentication).
:::

## Хорошо и плохо: примеры URI

| Плохо | Хорошо | Почему |
|---|---|---|
| `GET /getOrders` | `GET /orders` | Действие задаёт метод |
| `POST /orders/create` | `POST /orders` | То же |
| `GET /orders/delete/42` | `DELETE /orders/42` | `GET` не должен менять состояние |
| `GET /Order/42` | `GET /orders/42` | Множественное число, нижний регистр |
| `GET /orders/42.json` | `GET /orders/42` + `Accept: application/json` | Формат — через согласование |
| `GET /sales_Orders/42/lineItems` | `GET /sales-orders/42/line-items` | Единый стиль, kebab-case |
| `GET /customers/7/orders/42/items/3/taxes` | `GET /order-items/3/taxes` или `GET /orders/42/items/3` | Не глубже 2 уровней |
| `GET /orders?customerEmail=ivan@example.com` | `POST /orders/search` с email в теле | ПДн не в URL |
| `GET /orders?api_key=secret` | `Authorization: Bearer ...` | Секреты не в URL |
| `POST /orders/42/status` с телом `cancelled` | `POST /orders/42/cancel` | Явная бизнес-операция |
| `GET /orders/` и `GET /orders` ведут себя по-разному | Один канонический вариант | Предсказуемость |

## Полный пример CRUD для /orders {#crud-example}

::: code-group

```http [Создание]
POST /v1/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324

{
  "customerId": "7",
  "currency": "RUB",
  "items": [
    { "sku": "SKU-001", "quantity": 2, "price": "1500.00" }
  ]
}

HTTP/1.1 201 Created
Location: /v1/orders/42
ETag: "1"
Content-Type: application/json

{
  "id": "42",
  "status": "NEW",
  "customerId": "7",
  "currency": "RUB",
  "total": "3000.00",
  "createdAt": "2024-05-14T10:21:00Z"
}
```

```http [Чтение списка]
GET /v1/orders?status=NEW&sort=-createdAt&limit=20 HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json

{
  "data": [
    { "id": "42", "status": "NEW", "total": "3000.00", "createdAt": "2024-05-14T10:21:00Z" }
  ],
  "page": { "limit": 20, "nextCursor": "eyJpZCI6IjQyIn0" }
}
```

```http [Чтение элемента]
GET /v1/orders/42 HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
ETag: "1"
Content-Type: application/json

{ "id": "42", "status": "NEW", "customerId": "7", "total": "3000.00" }
```

```http [Частичное изменение]
PATCH /v1/orders/42 HTTP/1.1
Host: api.example.com
Content-Type: application/merge-patch+json
If-Match: "1"

{ "comment": "Позвонить перед доставкой" }

HTTP/1.1 200 OK
ETag: "2"
Content-Type: application/json

{ "id": "42", "status": "NEW", "comment": "Позвонить перед доставкой" }
```

```http [Бизнес-действие]
POST /v1/orders/42/cancel HTTP/1.1
Host: api.example.com
Content-Type: application/json

{ "reason": "CUSTOMER_REQUEST" }

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "42", "status": "CANCELLED" }
```

```http [Удаление]
DELETE /v1/orders/42 HTTP/1.1
Host: api.example.com

HTTP/1.1 204 No Content
```

:::

## HATEOAS и ссылки в ответе

HATEOAS (Hypermedia as the Engine of Application State) — ответ содержит ссылки на связанные ресурсы и доступные действия. Клиент переходит по ссылкам, а не собирает URL сам.

```json
{
  "id": "42",
  "status": "NEW",
  "_links": {
    "self":     { "href": "/v1/orders/42" },
    "customer": { "href": "/v1/customers/7" },
    "items":    { "href": "/v1/orders/42/items" },
    "cancel":   { "href": "/v1/orders/42/cancel", "method": "POST" }
  }
}
```

- Форматы: HAL (`_links`), JSON:API (`links`), Siren; в заголовке — `Link` (RFC 8288), часто для [пагинации](/design/pagination).
- Наличие ссылки `cancel` сообщает клиенту, что действие сейчас допустимо — бизнес-правила остаются на сервере.
- На практике в интеграциях «система — система» полный HATEOAS встречается редко: потребители работают по контракту OpenAPI. Минимально полезный уровень — `self`, ссылки пагинации и `Location` после создания.

## Типичные ошибки

- **RPC под видом REST**: `POST /api/execute` с полем `"action": "getOrder"` в теле — теряются кэширование, семантика методов и кодов. Если нужен RPC — берите [JSON-RPC](/protocols/json-rpc) или [gRPC](/protocols/grpc) осознанно.
- **Модель API = модель БД**: `/tbl_order_header`, поля `ord_hdr_id`. Любая миграция БД ломает клиентов.
- **Разный стиль в разных ресурсах**: `/orders?customer_id=` и `/invoices?customerId=`.
- **`GET`, меняющий состояние**: `GET /orders/42/confirm`. Прокси, краулеры и префетч браузера вызовут его без спроса.
- **Глубокая вложенность** и дублирование ресурса по нескольким путям.
- **`200 OK` на всё** с `"success": false` в теле. См. [Коды состояния](/http/status-codes) и [Ошибки](/design/errors).
- **ПДн и секреты в URL.**

## На что обратить внимание аналитику

- [ ] Ресурсы названы существительными во множественном числе, в нижнем регистре, kebab-case.
- [ ] Выбран и зафиксирован стиль JSON-полей и query-параметров (camelCase или snake_case).
- [ ] Вложенность не глубже двух уровней; у самостоятельных сущностей есть корневой путь.
- [ ] Для каждой бизнес-операции вне CRUD выбран способ (действие, событие, `PATCH`), описаны допустимые переходы и ответ на недопустимый.
- [ ] Определено, кто назначает ID (сервер или клиент), его формат и что ID — непрозрачная строка.
- [ ] Параметры разложены правильно: path — идентификация, query — выборка, header — метаданные, body — данные.
- [ ] В URL нет секретов и персональных данных.
- [ ] Описано поведение трейлинг-слэша и регистра.
- [ ] Для каждого эндпоинта: метод, успешный код, коды ошибок, заголовки (`Location`, `ETag`), [идемпотентность](/design/idempotency).
- [ ] Контракт оформлен в [OpenAPI](/specs/openapi) и согласован с потребителями до реализации.
- [ ] Учтены [версионирование](/design/versioning), [пагинация](/design/pagination), [фильтрация](/design/filtering), [ошибки](/design/errors), [соглашения о данных](/design/data-conventions).
